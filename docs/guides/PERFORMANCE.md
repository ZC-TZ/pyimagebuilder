# 构建速度与性能排查

[文档目录](../README.md) · [进度输出参考](../PROGRESS.md) · [缓存规则](../CACHE_POLICY.md)

先用日志判断时间花在哪里，再调整对应环节。参数以对应入口帮助为准，Fast 不提供全部 build 开关。网络传输量、解压后的层大小、文件数和最终 tar 大小不是同一个指标。

## 1. 分开比较三种运行

| 情况 | 包含什么 | 主要观察 |
| --- | --- | --- |
| 首次获取基础镜像 | 网络、解码、校验、入库和应用构建 | 网络尾部、层准备和 CAS 提交 |
| 基础镜像已在本地 | 本地读取/索引与应用构建 | 层文件数、磁盘、COPY |
| 应用指令缓存命中 | 复用应用层，仍需读基础镜像、写出和校验产物 | 缓存检查、导出和最终摘要 |

比较时固定包内容、基础镜像身份、平台、配置与时间戳，使用不同输出文件名。不要一边清缓存一边构建，也不要把 `--pull` 的刷新运行当成普通缓存命中。

## 2. 怎样看日志

`build` 和 `fast` 支持 `--progress plain`，适合保存逐行日志；`--progress json` 输出结构化事件。Web 可直接查看任务详情，导出范围是当前保留的最近 250 条。

例如，在 UOS 的 Bash 保存本次 CLI 输出：

```bash
set -o pipefail
python3 main.py fast /data/packages/hisq.war hisq 1.0.1 --profile tomcat --progress plain 2>&1 | tee hisq-build.log
```

`pipefail` 使构建失败不会被 `tee` 的成功状态掩盖。示例日志文件需放在构建上下文之外。

耗时表按操作耗时排序。**并行项、嵌套项不能直接相加**；总耗时看 `Duration`。条形只相对表内最长项，不代表总耗时百分比。

## 3. 按慢的阶段处理

| 阶段/现象 | 可能的主要成本 | 优先检查 |
| --- | --- | --- |
| 列目录与鉴权、探测文件大小 | API、认证或 HEAD 请求 | 完整 URL、协议、账号权限、仓库诊断 |
| 下载基础镜像文件 | 网络、连接数、单个大层 | Artifactory 的 workers、剩余文件数与速度 |
| 准备镜像层 | 解压、压缩摘要、DiffID、tar 结构校验 | CPU、磁盘空间、展开后大小 |
| 等待剩余层 | 网络结束时仍未完成的准备工作 | 活跃层和待处理数；不是又下载了一遍 |
| CAS 入库与提交引用 | blob 校验、同步落盘、引用验证 | 镜像库磁盘吞吐、可用空间 |
| 读取基础镜像与索引 / 应用基础层 | tar 成员数、whiteout、元数据 | 小文件数量、存储位置 |
| COPY/ADD 与缓存检查 | 枚举和哈希源文件、创建应用层 | 包大小、上下文范围、缓存目录 |
| 写出/校验归档、计算最终摘要 | 整包顺序读写、fsync | 输出盘、跨盘搬运与临时工作位置 |

下载尾部只剩一个大文件时，提高文件并发数通常不能提高该文件的速度。层编号可以乱序，判断完成进度应看“已完成”数量。

## 4. 当前会自动使用的优化

Artifactory CAS 路径先读取元数据，某层下载完成后立即开始准备，最多两层并行，与其他文件下载重叠；所有层成功后才提交引用。

普通 build/Fast 可以直接消费 CAS，不先组装巨大 base.tar。读取层时可复用当次验证取得的成员信息；多阶段 COPY 与 SBOM 在同次操作内复用层读取器。正常构建不会为了展示进度而跳过摘要或结构校验。

优化器计算文件签名时按层批量读取，并在候选层判断之间复用内容摘要，避免逐文件重新打开并扫描 tar。候选判断仍需要应用层来重建虚拟文件树，写出后也会独立复核，不能把优化耗时当成单纯压缩耗时。

缓存命中仍有 I/O：源输入检查、基础层读取、最终归档写出与校验不会因“命中”消失。`--verify-cache` 会增加完整读取，`--no-cache` 不刷新 FROM，`--pull` 也不关闭应用指令缓存。

## 5. 存储与工作目录

优先将 `cache.imageStore`、`cache.layerCache` 放在空间充足的本地磁盘。更改目录后，新目录没有旧数据，需要迁移原库或重新获取镜像；无需为正常代码更新主动删库。

跨盘导出可在输出盘的私有目录写出并校验，再以硬链接发布，减少整包复制。不支持或不满足条件时沿用原工作区。可通过 `--workspace /data/build-tmp` 显式固定工作位置；它必须位于构建上下文之外。

显式工作盘、输出盘及系统临时盘的表现需在目标机器对照。机械盘、网络盘、压缩和硬链接也会影响耗时与空间，不能直接套用别处的基准比例。

## 6. 空间与下一步

先运行 `python3 main.py system df`，或看 Web“空间”页。镜像库可能同时存放传输压缩 blob、解码层和按需 tar；交付下载还可能需要一份临时副本。

清理方式见[安全清理](TROUBLESHOOTING.md#怎么安全清理)。需进一步排查时，保留本次完整 CLI 日志，并说明首次下载还是本地复用、包大小、平台、磁盘位置和各阶段耗时。镜像性能对比仍需在实际 UOS/内网环境测量。
